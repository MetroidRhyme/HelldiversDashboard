This skill should be used whenever the user asks to work on, extend, troubleshoot, or debug the public Helldivers 2 live status page — the single-file static site that calls api.helldivers2.dev directly from the browser and is deployed via Cloudflare (no server, no scheduled scripts, no local PC dependency). Also load this before touching anything in this repo, or before assuming a Helldivers-related request is about the *other* project (see "Relationship to HelldiversMajorOrderWatcher" below — they share a data source but are otherwise independent).

## What this is

`index.html` — one self-contained HTML/CSS/JS file (~500KB, most of that base64-embedded faction/enemy icon images). No build step, no backend, no database. Every visitor's own browser fetches live data straight from `api.helldivers2.dev` (CORS-enabled, confirmed working — see Data source below) and renders it client-side. Built 2026-09-07 as a replacement for `HelldiversMajorOrderWatcher\web-dashboard.ps1` — the earlier version of this same idea, which ran a persistent `HttpListener` on Anthony's PC, LAN-only, needing manual `netsh`/firewall setup to reach from a phone. That script is now **retired** (task unregistered, listener stopped, 2026-09-07) — this repo is its full replacement, reachable from anywhere, nothing needs to be running on the PC at all.

## Architecture

**Everything runs in the visitor's browser. There is no server-side code in this project at all** — not a Worker function, not a Pages Function, nothing. The Cloudflare project just serves the static `index.html` file (confirmed via response headers: plain `cloudflare`/`CF-Cache-Status` headers, no custom backend). Every one of the fetches described below happens client-side, once per visitor, every ~60 seconds while their tab is open and visible.

**CORS was verified directly before building any of this** (2026-09-07, via a real headless-Edge browser fetch — not assumed from documentation): `api.helldivers2.dev` sends `Access-Control-Allow-Origin: *` and a proper preflight response (`Access-Control-Allow-Headers: X-Super-Client,X-Super-Contact`) on both the clean `/api/v1/*` endpoints and the `/raw/api/*` passthrough endpoints (see the modifier-badges entry below). `Cross-Origin-Resource-Policy: same-site` is also present on every response but does NOT block a cross-origin `fetch()` in `mode: "cors"` — confirmed by literally getting a successful response, not just by reading about CORP semantics (this is an easy thing to get wrong from documentation alone — a CORP header can look like it should block this and doesn't, at least not for a `cors`-mode fetch that also passes the ACAO check).

**Three page sections, in this order**: MAJOR ORDER / STRATEGIC OPPORTUNITY → PLANETS UNDER ATTACK (defend fronts) → ALL ACTIVE PLANETS (every planet with a live campaign, comprehensive — including planets already shown above, deliberately not deduped, per Anthony's explicit "list all active planets" request).

**The first two sections are a direct client-side port of `HelldiversMajorOrderWatcher\web-dashboard.ps1`'s own logic** — `resolveTaskPlanetIndex` (candidate-0/Super-Earth rejection), `getPlanetBlockStatus` (blocked/prereq detection via `waypoints`), `buildAssignmentRows`, `buildDefendRows`, `getPlanetProgress` (ownership-aware percent — health resets to full the instant a planet is actually liberated, so ownership is checked before health) are all straight JS translations of that PowerShell script's same-named functions. If a bug is found in one of these, check whether `lib\common.ps1` in the other repo has the same bug already fixed (or vice versa) — they've drifted into two independent copies (JS vs PowerShell) since there is no code-sharing between a browser page and a PowerShell project. See `[[project-helldivers-major-order]]`.

**Deliberately NOT ported**: the 5-tier seasonally-adjusted prognosis (`Get-Tier`), the recency-weighted regression against `history.db`, and the reconstructed Activity Log — all of those need real server-side history this static page has no access to. This was an explicit tradeoff Anthony accepted (asked directly, chose "keep it as-is" over adding a Cloudflare Worker Cron + D1 database for shared history) rather than something dropped silently.

### All Active Planets: diver counts, resistance rate, trend

Added 2026-09-07 (same day as the initial build), Anthony's request to see every active planet's diver count/percentage, "resistance rate", and whether current player count is enough to make progress.

- **Diver count/percentage**: `planet.statistics.playerCount` per planet, percentage of the SAME galaxy-wide total every other "player share" number on this page uses (`totalPlayers`, summed once from `/api/v1/planets`).
- **Resistance rate**: `planet.regenPerSecond` (a real, documented API field — health/sec the planet regenerates on its own, working against whatever damage divers do) converted to %/hr of the planet's own `maxHealth` via `getResistanceRatePctPerHr`. This is the closest real, honest answer to "resistance" — there is no other decay/pressure field anywhere in the API.
- **Trend ("enough divers?")**: the API gives no rate-of-change field at all (every endpoint is a live snapshot — confirmed by reading the full OpenAPI spec's `Planet`/`Event` schemas directly, not assumed). So each browser tab keeps its OWN short rolling memory (`planetHistory`, a `Map<planetIndex, [{t, percent}]>`) of what it has personally observed, sampled once per successful fetch (~60s). `getPlanetTrend` needs at least 4 minutes of real elapsed time between its oldest and newest sample before reporting a number (`PLANET_TREND_MIN_WINDOW_MS`) — shorter than that is mostly ±0.1%-rounding noise, not real signal (verified this specific noise floor by reasoning through the math, not just guessing at a nice round number). Shows "gathering data..." until then. Samples older than 20 minutes (`PLANET_TREND_WINDOW_MS`) are dropped.
  - **Persisted across reloads via `localStorage`** (added 2026-09-07, Anthony's request — "some basic history in cookie data"; implemented as localStorage, not an actual cookie, since there's no server here to send a cookie TO, and localStorage has a far larger size budget — see `loadPlanetHistory`/`savePlanetHistory`). Re-pruned against the CURRENT time on load, not trusted as saved — a tab reopened hours later correctly falls back to "gathering data..." rather than showing an hours-stale rate. Verified via two separate headless-Edge launches sharing one `--user-data-dir` profile: a seeded 6-minutes-old sample survived into a completely fresh page load and combined with a live read to produce a correct real-time rate.
  - **Resistance-aware wording fix** (2026-09-07, Anthony reported seeing "not enough divers to outpace resistance" on a planet also showing 0%/hr resistance — a real bug: blaming "resistance" when there IS none is misleading). `getPlanetTrend` now takes the planet's own `resistanceRate` and only uses that wording when resistance is meaningfully above zero (`> 0.05%/hr`); otherwise it says "too few active divers to move the needle". Only the flat case needed this — a real observed up/down rate doesn't need the caveat.
- **Sort control**: pill buttons (Divers / Progress — a "Number" option, sorting by the API's raw internal planet index, was added then removed same day at Anthony's request once he saw it did nothing meaningful). Persisted in `localStorage` (`hd2dash_activeSortMode`) as a pure per-browser convenience, never load-bearing. Switching sort mode only re-renders already-cached data (`sortActivePlanetRows`) — no refetch.
- **Planet details**: sector + biome + hazards line, reusing `getPlanetConditionsText` (already used by the other two sections) — added because Anthony asked for it after the initial build shipped without it.
- **Defense pace comparison, also shown here for any active-planet row currently under an event** (added 2026-09-07, extracted into a shared `getDefensePaceInfo(planet, progress, nowUtc)` used by BOTH this section and Planets Under Attack, so they can never drift apart) — see next entry for the full reasoning.

### "Are we winning?" — defense pace comparison

Anthony asked to see "enemy progress" on defense events so he could tell if a defense was being won. **Checked the live `event` object directly first, before building anything** — its real fields are `id, eventType, faction, health, maxHealth, startTime, endTime, campaignId, jointOperationIds`. No separate enemy-progress field exists (confirmed against both a live API response AND the OpenAPI spec's `Event` schema). So `getDefensePaceInfo` compares the two REAL quantities the API does give: `progress.percent` (how much of the defense is actually repelled) vs. `elapsedPercent` (how much of the event's own time window has already run out). More than 5 points ahead → "Ahead of pace - likely to hold" (green); more than 5 behind → "Behind pace - at risk" (red); otherwise "On pace - too close to call" (amber). Rendered as a second, compact 6px bar (no header caption — Anthony asked for this to be smaller/tighter after the first version) sitting right under the main defense-progress bar, plus the plain-language status line. Verified against the one live defense event at build time (BEKVAM III: 10.5% defended vs 16.6% elapsed → correctly "Behind pace") with a hand calculation matching exactly.

### Planet modifiers (Jet Brigade, Hive World, etc.)

Added 2026-09-07, Anthony's question ("can you see Jet Brigade or Hive Planet from the API?"). **This required real investigation, not something obvious from the endpoints already in use — re-read this before assuming it can't be done again:**

- The clean `/api/v1/planets` endpoint has **no** effects/modifiers field at all — checked its full schema directly in the OpenAPI spec (`index, name, sector, biome, hazards, hash, position, waypoints, maxHealth, health, disabled, initialOwner, currentOwner, regenPerSecond, event, statistics, attacking, regions` — that's genuinely everything).
- The data DOES exist, but only via a **raw passthrough of Arrowhead's own backend** — `api.helldivers2.dev/raw/api/WarSeason/{warId}/Status` (get `{warId}` from `/raw/api/WarSeason/current/WarID` first — two sequential calls). This mirrors Arrowhead's real, uncleaned API response and has a `planetActiveEffects` array: `[{index, galacticEffectId}, ...]`. Confirmed CORS-enabled the same way `/api/v1/*` is (same preflight/ACAO headers).
- `galacticEffectId` only turns into a real name via a SEPARATE static reference table — `github.com/helldivers-2/json`'s `effects/planetEffects.json` (~34KB, 156 entries as of 2026-09-07: `{galacticEffectId, name, description}`). This is the same reference repo `HelldiversMajorOrderWatcher` already uses for `task.type`/`race`/faction lookups — see that project's skill doc.
- **`PLANET_MODIFIER_NAMES`** (in `index.html`) is a hand-curated subset of that 156-entry table — the ~13 "enemy special force" modifiers (Jet Brigade, Hive Lords, Cyborgs, Predator Strain, Dragonroaches, Rupture Strain, Spore Burst Strain, Incineration Corps, Mindless Masses, Appropriators, Heavy SEAF Presence, Vote Snatchers, Invasion Fleet) plus Hive World specifically, deliberately excluding the other ~140 flavor/infrastructure effects (city names, one-off stratagem-arsenal unlocks, etc. — Anthony's own suggestion to keep this to combat-relevant modifiers). Most named modifiers appear as TWO separate `galacticEffectId`s in the live data (a plain id and an "(Enemies)"-suffixed one meaning the same thing — e.g. 1202+1203 both mean Jet Brigade) — both map to one shared display name so a planet with both only shows one badge.
- **This table is a snapshot, not automatically kept current.** A new `galacticEffectId` introduced by a future game update (a new enemy special force, etc.) will silently show NO badge for that planet until someone notices and adds it — same "extend by hand when you see a new one" pattern as `KnownUnitNames` in the other project. To add one: cross-reference the unrecognized id against a fresh pull of `effects/planetEffects.json`.
- Fetching this is a fully optional enhancement (`fetchPlanetModifiers`), run in parallel with the main `assignments`/`planets`/`campaigns` fetch via `Promise.all` but with its OWN internal try/catch — a failure here degrades to "no badges shown" and is logged to the console, but can never turn the rest of a working page into an error banner. This raises the real per-refresh API call count from 3 to 5 (well within the shared 5 req/10s limit for a personal-scale audience, but worth remembering if this project's traffic ever changes materially).
- Verified against real live data (not just the reference table read): OMICRON showing Dragonroaches + Hive Lords + Hive World simultaneously (its `biome.name` is ALSO "Hive World" — a nice independent cross-check that the badge is correct), plus Cyborgs/Vote Snatchers/Appropriators/Invasion Fleet/Mindless Masses/Heavy SEAF Presence on other planets, all matching a direct hand cross-check of the raw response against the name table.

### Region (settlement) status labeling — "liberated" vs "not yet open for missions"

Added 2026-09-10, prompted by Anthony reporting UTOPIA VAREN (a region/settlement on CHARBAL-VII) showing "870 divers - 0% cleared - not yet open for missions" when he believed — correctly, per his own in-game play — that it had just been liberated.

- **Investigated first via `HelldiversMajorOrderWatcher`'s `history.db`**: CHARBAL-VII's own top-level `health` sat completely flat at `maxHealth` (0% progress) for ~4 days despite tens of thousands of players on it — consistent with that project's own already-documented "planet-level liberation doesn't move until the region under it is captured" finding (see that project's skill doc, 2026-09-08 entry). Then, in a single 15-minute window (02:26→02:41 UTC 2026-09-10), the planet's health suddenly dropped ~1.5M points and kept draining afterward — a strong signature of the region gate having just opened.
- **The region field itself told a misleading story at that exact moment**: a live `/api/v1/planets/156` call showed UTOPIA VAREN at `health == maxHealth` (0% by the naive `(maxHealth-health)/maxHealth` formula) and `isAvailable: false` — reading as "untouched, locked," the opposite of what had just happened.
- **Root cause: the same reset-to-full-on-completion quirk `HelldiversMajorOrderWatcher` already found and fixed for whole planets (`getPlanetProgress`/`Get-PlanetProgress` — checking `currentOwner` before trusting `health`), now confirmed at the region level too** — except a region carries no ownership field of its own to check, only `isAvailable`. Anthony's live, in-game confirmation ("this looks like `isAvailable:false` means the settlement has been liberated") is the actual evidence this rule is based on — not something derivable from the API schema alone.
- **Genuine, unresolved ambiguity, stated plainly in the code comment**: a never-yet-unlocked region and an already-captured one both read identically (`health == maxHealth`, `isAvailable: false`) — there is no field that tells them apart. `regionsHtml` now treats that combination as "liberated" (100% cleared) rather than "not yet open for missions", per Anthony's confirmation, but this is a heuristic on one confirmed data point, not a documented API contract — same confidence tier as `HelldiversMajorOrderWatcher`'s own "reverse-engineered heuristic" fields (see that project's skill doc's Data source section). If a region ever shows "liberated" that Anthony knows is wrong (e.g. a settlement that's never been touched), that's the case this heuristic can't distinguish — revisit then.
- **Not backfilled into `HelldiversMajorOrderWatcher`** — that project doesn't render region rows at all yet (its own skill doc's "Known gap" entry, 2026-09-09, still stands: `history.db` doesn't log `regions`). This fix only touches this project's own client-side `regionsHtml`.

## Testing convention

**Every change in this project was verified by actually rendering it before shipping — via a real headless-Edge screenshot, not by reading the code and trusting it.** This caught a real bug during the initial build (a malformed flex-wrapper in `rowHtml` that squeezed row labels into a vertical one-character-per-line column — invisible from reading the code, obvious from a screenshot) and is the same "verify by looking, not by trusting the code" discipline `HelldiversMajorOrderWatcher`'s own doc calls out repeatedly. The pattern used throughout this project's build:

1. Copy `index.html` to a scratch file, substitute `%%CONTACT_EMAIL%%` with a placeholder (the real file ships with that literal token unreplaced — see below).
2. For a REAL-data check: leave `hd2Fetch` untouched, just screenshot the page against live data.
3. For a SYNTHETIC-data check (needed to exercise states that aren't live right now — a specific blocked/prereq combo, a specific trend direction, a specific resistance value): remove the trailing `refreshAndRender(true);` bootstrap call, append a new `<script>` block that overrides the global `hd2Fetch` function with a mock returning fabricated `assignments`/`planets`/`campaigns` JSON (matching the real API's shapes — see the real fixtures fetched during this project's build for reference shapes), then call `refreshAndRender(true)` manually. This works because `hd2Fetch` is a plain top-level `function` declaration (a mutable global binding) — reassigning it in a LATER `<script>` tag redirects every future call, since JS resolves the identifier at call time, not definition time.
4. For a PERSISTENCE check (localStorage across a reload): two separate headless-Edge launches sharing one `--user-data-dir` profile directory — Chromium partitions `localStorage` by profile, not by exact `file://` path, so this reliably simulates "close tab, reopen" behavior.
5. Render via `msedge.exe --headless --disable-gpu --window-size=<W>,<H> --virtual-time-budget=9000 --screenshot=<path> <url-or-file>`, then read the PNG. Always pick `H` generously — this project's rows are variable-height (enemy portraits, modifier badges, multi-line details), so a too-short window silently clips content rather than erroring.
6. **`node --check` on the extracted `<script>` contents catches a syntax error before ever bothering with a browser render** — cheap, and caught a real typo during this project's build (a stray `#` where a `//` comment continuation was meant, which would have been a silent blank-page failure in production otherwise since there's no server-side build step to catch it).

Before pushing to `master` (which auto-deploys), verify the live URL actually reflects the new deploy — Cloudflare's git-triggered deploy isn't instant. Poll `curl -s https://helldivers.evoveriv.com/ | grep "<some string unique to the new code>"` in a short retry loop rather than assuming a push means it's already live.

## Relationship to HelldiversMajorOrderWatcher

Same underlying game/API/community, but architecturally independent projects — **don't assume a fix or fact in one automatically applies to the other**, even though a lot of the core game-data logic (task-to-planet resolution, blocked/prereq detection, ownership-aware percent) started as direct ports and can drift:

| | HelldiversMajorOrderWatcher | HelldiversDashboard (this project) |
|---|---|---|
| Runs | Scheduled PowerShell scripts, Anthony's PC | Nothing — static file, Cloudflare CDN |
| Needs the PC on? | Yes, for every feature | No — fully independent since 2026-09-07 |
| History/trend | Real `history.db` (SQLite), full regression | Client-side rolling memory only, `localStorage`-persisted, per-visitor |
| Audience | Discord channel (posted to) | Public URL (pulled, by anyone who visits) |
| Secrets | `config.ps1` (Discord webhook — real secret) | None at all |
| Self-ID headers | Anthony's real email (fine — never leaves his own script/logs) | A generic project identifier (public-facing — see Data source) |

The old `web-dashboard.ps1` (the LAN-only predecessor to this whole project) is **retired** as of 2026-09-07 — see that project's own skill doc for the retirement note. If a future request sounds like "the web dashboard" and is ambiguous which project it means, this one (the public Cloudflare page) is almost certainly what's meant now; the PC-based one no longer exists to be confused with.
